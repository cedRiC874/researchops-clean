# 合成清洗评测

此工具生成一张标准答案表，再注入已知错误，用于检验清洗程序是否正确恢复、标记和保留单元格。全部数据由程序合成，不联网、不调用模型，不使用真实病人数据，也不生成姓名、身份证号、电话或地址。

**参考配方仅用于评测。合成取值范围和范围检查界限是工程测试参数，不是临床参考范围；真实数据必须由人审核、填写参数并批准。**

这项提醒同时写入生成目录的固定 `README.md`，其哈希收录在 `bench_manifest.json`；参考配方每一步的理由均以 `【仅用于评测】` 开头。参考步骤预先由 `bench-reference` 批准，以便重复运行工程测试，不能据此批准真实数据的清洗规则。

批准同时绑定输入文件的 SHA-256 和该步骤的 `step_id`、`op`、`params`，记录在 `approval.content_sha256` 中；`reason` 不参与绑定。改变输入哈希或上述步骤内容后必须重新批准。旧配方的批准记录若没有此哈希，也必须重新运行 `approve`，不会自动兼容。该哈希用于检查批准内容是否仍然一致，不是审核人身份的数字签名。

旧生成目录中的参考配方若没有批准内容哈希，要继续完整评估须重新 `generate` 到新目录，确保参考配方与基准文件清单一致。普通旧配方可运行 `approve` 另存新配方后执行；不要手工补写哈希。新生成的参考配方通过统一的批准流程绑定其输入和步骤，仍保留固定的评测审核人及批准时间。

批准内容哈希保留 Unicode 原文，将输入 SHA-256、`step_id`、`op`、`params` 按键排序、紧凑 JSON 格式序列化为 UTF-8 后计算 SHA-256，不做 Unicode 归一化。它不使用会进行 NFC 归一化的 `ledger.sha256_json`，从而区分原文不同的列名或映射字符串；账本的既有哈希规则不变。CSV 读取保留原列名，但任意两个列名经 NFC 归一化后相同时会以 `ambiguous_column_names` 拒绝，须人工修正歧义后再使用。

## 生成的数据

标准答案 `clean.csv` 固定包含 8 列：住院号、出生日期、性别、采样时间、项目、结果、单位、年龄。同一患儿有多条记录，编号为带前导零的随机 7 位数字。出生日期、采样日期均为 `YYYY-MM-DD`，采样晚于出生，年龄在 0–14 岁之间；年龄按两日期计算为中文岁、月、天表示。性别仅使用“男”“女”。

结果按固定一位小数写成字符串，取值网格步长为 `0.1`：

| 项目 | 标准单位 | 工程生成范围 |
|---|---|---|
| 血红蛋白 | g/L | 80.0–160.0 |
| 白细胞计数 | ×10^9/L | 2.0–15.0 |
| 超敏C反应蛋白 | mg/L | 0.0–20.0 |
| 血糖 | mmol/L | 2.5–9.5 |

这些范围只定义合成数据，不能用于判断真实检验结果是否正常。

## 注入错误

同一脏表单元格最多记录一种错误。每条错误均记录脏表行号、列、干净值、脏值、错误类型和处理期望。

| 类型 | 注入方式 | 评估期望 |
|---|---|---|
| `date_format` | 将采样日期改为带时间的斜杠格式、紧凑日期或 Excel 序列号 | `restore`：还原标准日期字符串 |
| `sex_code` | 将男、女改写为 1/2 或 M/F | `restore` |
| `item_alias` | 使用 HGB、Hb、WBC、GLU 等项目别名 | `restore` |
| `unit_variant` | 血红蛋白改为 g/dL，数值除以 10；血糖改为 mg/dL，数值乘以 18 | 结果和单位两个单元格均为 `restore` |
| `fullwidth_space` | 结果使用全角数字，或在首尾增加空格 | `restore` |
| `sentinel` | 年龄改为“999”，或采样日期改为“1900-01-01” | `to_missing`：变为空且有对应标记 |
| `impossible_value` | 血红蛋白结果多录一个 0 | `flag_only`：标记异常，允许保留原值 |
| `duplicate_record` | 插入已有记录的副本，副本可以带一种写法变化 | `flag_only`：原记录和副本均有重复标记 |

除重复记录默认比例为 `0.02` 外，其余类型默认比例为 `0.03`。比例针对各类型适用的候选行或单元格：例如别名只涉及有别名的项目，单位变体只涉及血红蛋白和血糖，异常值只涉及血红蛋白。缺失代码以年龄和采样日期两列的候选单元格计算，重复记录按原始行数计算复制次数。

比例是注入目标，实际数量还受候选数量和单元格不得重叠的约束；候选不足时按可用数量截断。`event_counts` 记录注入事件数，`error_counts` 记录 `truth.json` 中的错误单元格条数，两者不能混用。单位变体一次事件通常对应两个错误单元格；重复事件涉及原记录和副本的多个单元格，副本上的写法变化单独按相应 `restore` 类型计数。默认重复比例约影响 4% 的单元格，具体以实际清单为准。

## 命令

安装本项目的锁定依赖后，在项目根目录运行独立入口。它不经过主清洗命令的模型提案分支。

```sh
python -m researchops_clean.bench generate --rows 2000 --seed 7 --output-dir artifacts/bench/b1
```

`--rows` 默认 `2000`，`--seed` 默认 `7`。可为不同错误类型重复使用 `--rate`，每种类型只能指定一次，比例在 `0`–`1` 之间：

```sh
python -m researchops_clean.bench generate --rows 200 --seed 7 --rate date_format=0.05 --rate duplicate_record=0.02 --output-dir artifacts/bench/small
```

同一种子和全部生成参数会产生逐字节相同的输出；生成时不使用当前时间或全局随机状态。生成目录包含：

| 文件 | 用途 |
|---|---|
| `clean.csv` | 标准答案 |
| `dirty.csv` | 注入错误后的输入，可能包含额外的重复记录 |
| `truth.json` | 错误单元格和脏行到干净行的对应关系 |
| `reference_recipe.json` | 仅用于评测的已批准参考配方 |
| `reference_column_map.json` | 参考配方的原列、派生列对应关系 |
| `README.md` | 固定的评测用途警示和数据说明 |
| `bench_manifest.json` | 参数、种子、版本、文件哈希、事件数和错误单元格数 |

执行参考配方、核验并评估：

```sh
python -m researchops_clean apply --input artifacts/bench/b1/dirty.csv --recipe artifacts/bench/b1/reference_recipe.json --output-dir artifacts/cleaning/bench-run-01
python -m researchops_clean verify --input artifacts/bench/b1/dirty.csv --recipe artifacts/bench/b1/reference_recipe.json --run-dir artifacts/cleaning/bench-run-01
python -m researchops_clean.bench evaluate --bench-dir artifacts/bench/b1 --run-dir artifacts/cleaning/bench-run-01 --column-map artifacts/bench/b1/reference_column_map.json --output-dir artifacts/bench/eval-01
```

生成和评估输出都必须是项目 `artifacts/` 下尚不存在的独立子目录。结果先写入临时目录，再整体发布，已有目标不会被覆盖。所有 CSV 单元格按字符串处理，输出采用 UTF-8 无 BOM、LF 换行。

## 评估口径

评估先检查 `apply` 输出的四个文件完整，且 `run_manifest.json` 中记录的文件哈希与实际内容一致；缺文件或哈希不符直接拒绝评估。评估不按值猜测行关系，而是使用 `truth.json` 将每一条脏表行与对应的标准答案行对齐，因此插入的副本不会造成后续行错位。

`--column-map` 必须指向 JSON 对象，例如：

```json
{"采样时间": "采样日期", "结果": "结果数值"}
```

未指定的标准答案列按同名列比较；指定的列从清洗结果对应列取值。映射也用于判断原列或派生列上的标记归属于哪个标准答案单元格，不会因为解析新增列而漏算标记。标记优先归属于该列作为映射目标所对应的标准列；不属于任何映射目标时，才按原标准列名关联，因此交换列名不会把一个标记计入两个单元格。未映射且不是原标准列的额外派生列不参与逐单元格误报计数。

| 单元格类型 | 判断 |
|---|---|
| `restore` | 等于干净值计“修对”；与脏值不同但不等于干净值计“改错”；仍等于脏值计“漏掉” |
| `to_missing` | 值为空且该行对应列有标记计“处理对”；其他情况计“漏掉” |
| `flag_only` | 对应行、列有标记计“标出”；重复记录看任一键列的重复标记；否则计“漏掉” |
| 没注入错误的单元格 | 与干净值不同计“误改”；有对应标记计“误报” |

比较采用字符串完全相等，不用浮点容差，也不降低小数位要求。参考配方通过公开、固定的完整数值网格对照表恢复一位小数，兼容已有操作去掉末尾零，以及血糖按有限十进制系数换算时产生的尾数。该表独立于本次种子、生成行和 `truth.json`，不逐格抄标准答案。

评估输出 `evaluation.json` 和中文 `summary.txt`，按错误类型记录注入数、修对、改错、漏掉、标出，并记录未注入单元格的误改、误报，以及 bench 和 run 的哈希。数量来自实际错误单元格，不是将注入比例当作得分。

同样的评估输入产生逐字节相同的两个输出。`evaluation.json` 的 `created_at_utc` 固定为 `2026-01-01T00:00:00Z`，它是基准版本使用的固定时间标记，不是实际评估时刻，也不参与 `evaluation_hash` 的计算。

`generate`、`evaluate` 成功均返回 `0`。参数、输入、文件哈希、列映射或输出目录不合法返回 `2`，并输出不含本机绝对路径的中文错误 JSON。**评估结果好坏不影响退出码**：能完整评估但漏改很多，仍然返回 `0`。

## 扩展真实字段配置

拿到经过审核的真实字段清单后，可以新增一份合成生成配置，描述字段名称、字符串格式、项目与单位、可用别名、可注入的错误类型和每种错误的处理期望。医学界限应由医生提供；工程生成范围不能直接移植为医学规则。

新增配置仍应自行生成合成记录，不复制真实病人行；同时补充对应的 truth、列映射、参考配方和小规模测试，沿用相同的行对齐和评分口径。新的参考配方也只用于评测，实际数据处理继续走人工批准流程。
